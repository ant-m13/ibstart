# Участие в разработке IBStart

Спасибо за интерес к проекту. IBStart — нативное приложение Windows на C++20; изменения должны оставаться понятными, безопасными для пользовательских списков `ibases.v8i` и совместимыми с Windows 10 и Windows 11 x64.

## До начала работы

1. Проверьте открытые issue и pull request, чтобы не дублировать работу.
2. Для ошибки, новой возможности или вопроса используйте соответствующую форму в разделе **Issues**.
3. Не публикуйте пароли, токены, реальные строки подключения, дампы с персональными данными или пути, раскрывающие данные пользователя. Вопросы безопасности описаны в [SECURITY.md](SECURITY.md).
4. Придерживайтесь [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md).

## Локальная проверка

Требуются Visual Studio Build Tools 2022 или новее с компонентом **Desktop development with C++**, CMake 3.24+, Ninja и Windows SDK. В x64 Native Tools Command Prompt из корня репозитория выполните:

```powershell
cmake --preset msvc-x64-release
cmake --build --preset msvc-x64-release
ctest --preset msvc-x64-release
```

Перед отправкой изменений также проверьте, что `git diff --check` не выводит ошибок. Не добавляйте в commit содержимое `out/`, `.vs/`, пользовательские файлы `data/` или журналы.

## Правила для изменений

- Используйте C++20 и существующий стиль Win32-кода; не вводите внешние runtime-зависимости без обоснования.
- Логи не должны содержать пароли, токены или исходные значения параметра `/P`.
- Операции очистки должны принимать только явно разрешённые каталоги и не могут удалять файлы информационных баз.
- Для изменения логики ядра добавляйте или обновляйте unit-тесты в `tests/unit/test_main.cpp`.
- Для пользовательских изменений обновляйте `README.md` и `docs/user-guide.md`, если поведение приложения или команды интерфейса меняются.

## Версия и релиз

Каждый pull request, предназначенный для включения в выпуск, обновляет единственный источник номера — `cmake/IBStartVersion.cmake` — и добавляет раздел с тем же номером в `CHANGELOG.md`. Номер использует SemVer без build metadata. После merge в `main` GitHub Actions собирает, тестирует и публикует релиз; подробности находятся в [docs/release-process.md](docs/release-process.md).

## Pull request

Опишите пользовательский эффект, укажите связанные issue и перечислите выполненные проверки. Держите pull request сфокусированным: независимые изменения оформляйте отдельно. До merge должны успешно завершиться обязательные проверки GitHub Actions.
