# Архитектура IBStart

IBStart придерживается правила направленных зависимостей: ядро не зависит от окна Win32. UI получает данные от ядра и отображает ошибки, но не разбирает `ibases.v8i`, не формирует командную строку и не пишет файлы напрямую.

```text
src/
├── app (точка входа и повторная активация экземпляра)
├── core
│   ├── domain
│   ├── connection
│   ├── v8i (документ и безопасное атомарное хранилище ibases.v8i)
│   ├── catalog
│   │   ├── catalog (дерево и операции над записями)
│   │   ├── catalog_metadata_service (теги, избранное и история)
│   │   └── catalog_session (связка файла, каталога и платформ)
│   ├── platform (поиск установок и сравнение версий)
│   ├── launcher
│   │   ├── command_builder (параметры, выбор платформы и аргументы)
│   │   └── process_launcher (единственный CreateProcessW)
│   ├── scanner (поиск файловых баз)
│   ├── cache (разрешённые кэши 1С и их очистка)
│   ├── shell (создание ярлыков через COM)
│   ├── logging (маскирование секретов и ротация журналов)
│   ├── update
│   │   ├── github_release_client (WinHTTP-транспорт)
│   │   └── update_service (SemVer и политика обновлений)
│   └── storage
│       ├── storage_paths (layout, portable mode и стандартный список)
│       ├── json_codec (разбор и экранирование JSON)
│       └── storage (файлы настроек, состояние каталога и атомарная запись)
└── ui (тонкий Win32-слой)
    ├── main_window (координация окна и маршрутизация сообщений)
    ├── command_dispatcher (таблица команд и динамические диапазоны)
    ├── tree_view_controller + tree_presentation
    ├── details_view_controller
    ├── menu_controller + context_menu_controller + command_ids
    ├── database_editor_dialog + advanced_database_options_dialog
    ├── tag_manager + tag_*_dialog
    ├── update_check_operation + cache_clear_operation
    └── dialog_support / folder_picker / input_box / owner_draw_menu
```

`domain` определяет типы базы, платформы и команды запуска. `connection` разбирает `File`, `Srvr`/`Ref` и веб-подключения, не меняя исходную строку. `v8i` хранит секции и поля в исходном порядке: поле, которое ядро не знает, не преобразуется и сериализуется на прежнем месте среди полей. `catalog` строит дерево по `Folder` за один проход с индексом дочерних элементов, кэширует регистронезависимый поиск секций по имени и ID, понимает нативные абсолютные пути 1С (`/`, `/Группа/Подгруппа`) и хранит ручной порядок в `OrderInList` и `OrderInTree`.

`V8iFileStore` запоминает fingerprint прочитанного файла. При сохранении он захватывает именованный mutex для конкретного пути и удерживает его от первой проверки до commit через `MoveFileExW`; перед backup и непосредственно перед заменой размер, время записи и хеш сравниваются с загруженным fingerprint. Это сериализует экземпляры IBStart, использующие тот же протокол, и не допускает их взаимной потери обновлений. `MoveFileExW` остаётся отдельной атомарной операцией замены: Windows не предоставляет для произвольных внешних редакторов compare-and-swap по пути, поэтому программа, не участвующая в mutex-протоколе, может изменить файл в коротком остаточном окне перед заменой. Документация не обещает защиты от такого неподконтрольного writer; после работы стороннего редактора список нужно перечитать перед сохранением, а после обнаруженного конфликта — обязательно перезагрузить.

`launcher/command_builder` содержит чистые функции выбора платформы, разбора дополнительных параметров и построения аргументов. Выбор сначала учитывает совместимость версии, затем ограничения клиента и разрядности; при одинаковой версии автоматический режим предпочитает x64, а `x86_prt` — x86. Формирование полной строки для `LaunchCommand` также остаётся частью построителя. Единственный Win32-вызов `CreateProcessW` изолирован в `launcher/process_launcher.cpp`; он принимает уже подготовленную команду и не знает о выборе платформы. `scanner` рекурсивно находит каталоги с `1Cv8.1CD` и возвращает результаты без изменения каталога. `shell` создаёт ярлык на сам IBStart с идентификатором базы, не помещая пароль в командную строку. Тесты покрывают чистую часть без создания окон.

`storage` использует `%LOCALAPPDATA%\IBStart` или `data` возле EXE в portable mode. Активный `ibases.v8i` не дублируется. `logging` маскирует известные секретные параметры и присваивания, включая значения в URL `/WS`, а полный операнд fallback-строки скрывает до записи. Это правило относится к журналам и автоматически создаваемым diagnostics; UI и буфер обмена по явному действию пользователя сохраняют исходное значение. `cache` намеренно принимает только список разрешённых cache-подкаталогов (`%APPDATA%\1C\1Cv8`, `%LOCALAPPDATA%\1C\1Cv8`, `%LOCALAPPDATA%\IBStart\cache`), никогда не путь из `Connect`, и отказывается очищать подкаталоги лицензий. Наличие процессов клиента `1cv8.exe` и `1cv8c.exe` проверяется только для предупреждения: очистка остаётся best effort, не завершает процесс и продолжает обработку остальных разрешённых каталогов, собирая ошибки отдельных каталогов. Полные схемы и правила совместимости файлов описаны в [configuration.md](configuration.md).

`update/github_release_client` по явной команде пользователя получает небольшой release asset `IBStart.version` через стабильную HTTPS-ссылку GitHub `releases/latest/download`, без обращения к REST API. Он отвечает только за WinHTTP, тайм-ауты, HTTP-статусы, ограничение размера ответа и кооперативную отмену. `update/update_service` читает только SemVer-версию, строит ссылку на страницу релиза и сравнивает версии; он не скачивает исполняемые файлы, не меняет EXE и не сохраняет историю проверок. Сетевой запрос выполняется вне потока окна; UI получает лишь готовый результат.

`ui/main_window` координирует жизненный цикл окна, маршрутизацию сообщений и обновление представлений. Идентификаторы команд централизованы в `command_ids`, таблица обработчиков и диапазоны динамических команд — в `CommandDispatcher`, а создание и обновление верхнего/файлового меню, owner-draw состояния и native menu handles инкапсулированы в `MenuController`. `ContextMenuController` отдельно строит контекстные меню дерева и деталей, владеет их owner-draw пунктами и возвращает выбранную команду; окно передаёт ему только снимок состояния и применяет результат. Заполнение дерева и операции с native tree view находятся в `TreeViewController`: `Populate` синхронизирует целевую структуру с существующими `HTREEITEM`, переиспользует неизменившиеся строки и пересобирает только ветку с изменившимся порядком; обновление выполняется с подавлением промежуточной перерисовки и сохранением раскрытых веток, выбранной строки и видимой позиции. Ветка «Недавние» обновляется тем же частичным механизмом. `tree_presentation` готовит отфильтрованную проекцию дерева одним проходом с кэшированием результатов поиска и фильтра тегов, а также отвечает за отрисовку; ввод поискового текста обновляет дерево через короткую задержку таймера, чтобы серия нажатий не запускала отдельные перестроения. Сведения о выбранной базе находятся в `DetailsViewController`. `CatalogSession` загружает связку `V8iFileStore`, `Catalog` и найденных платформ, оставляя UI только переключение состояния и отображение ошибок. Редактор базы и окно дополнительных параметров являются отдельными диалоговыми модулями; `TagManager` координирует формы тегов и сохранение метаданных, а `update_check_operation` и `cache_clear_operation` владеют фоновыми потоками. Низкоуровневые общие операции Win32-диалогов находятся в `dialog_support`.

`storage/storage_paths` разрешает расположение данных (обычный или portable mode), проверяет доступность каталога и ищет стандартные файлы 1С. `storage/json_codec` содержит минимальный JSON-кодек, используемый хранилищами; он не знает о настройках и тегах приложения. `storage/storage` отвечает за атомарное чтение/запись файлов и преобразование JSON в `Settings` и `CatalogState`, а `CatalogStateRepository` добавляет кэширование и транзакционные обновления состояния.

Версия продукта задаётся только в `cmake/IBStartVersion.cmake`. На этапе конфигурации CMake из неё генерируются C++ header, Windows VERSIONINFO, manifest, `ibstart-version.txt` и пустой маркер `IBStart.portable` для portable-архива. Благодаря этому окно «О программе», свойства PE-файла и release workflow используют одно значение.

## Тестируемость

`tests/unit/test_main.cpp` — самостоятельный CTest-исполняемый файл без фреймворка. Он использует fixtures, не открывает окна и проверяет round trip, сохранение/backup/conflict, команды запуска, выбор x64, маскирование `/P`, portable mode, SemVer-сравнение и разбор release asset `IBStart.version`.
