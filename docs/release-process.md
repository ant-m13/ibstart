# Выпуск IBStart

Релиз создаётся автоматически после принятия pull request с изменениями приложения в `main`. Изменения только в `docs/**`, `README.md`, `CHANGELOG.md`, `mkdocs.yml`, `requirements-docs.txt` и `.github/workflows/**` не запускают `release.yml`. Прямой ручной выпуск по тегу не требуется.

## Подготовка pull request

1. Измените единственный источник версии в `cmake/IBStartVersion.cmake`. Используйте SemVer без build metadata, например `0.7.2` или `1.0.0`.
2. Добавьте в `CHANGELOG.md` раздел с тем же номером и описанием пользовательских изменений.
3. Локально выполните Release-сборку и тесты:

   ```powershell
   chcp 65001
   cmake --fresh --preset msvc-x64-release
   cmake --build --preset msvc-x64-release --clean-first
   ctest --preset msvc-x64-release
   ```

   Для выпуска используйте полную пересборку. На локализованном MSVC кодовая
   страница при определении компилятора должна совпадать с выводом компилятора:
   ошибочно распознанный префикс `/showIncludes` оставляет Ninja без зависимостей
   от заголовков. `chcp 65001` перед `cmake --fresh` устраняет обнаруженное
   несовпадение UTF-8/OEM на русской установке Build Tools. Убедитесь, что
   `ninja -C out/build/msvc-x64-release -t deps` содержит зависимости от заголовков.

4. Проверьте справочные данные без исходных страниц 1С:

   ```powershell
   python tools/update-1c-reference.py --check
   python tools/update-launch-parameter-versions.py --check-docs
   python -m unittest discover -s tools/tests -p "test_*.py"
   ```

5. Соберите сайт командой `mkdocs build --strict`, временно скопировав `CHANGELOG.md`
   в `docs/changelog.md`, и удалите временную копию. Проверьте локальные ссылки,
   якоря и изображения в сгенерированных страницах.
6. Создайте pull request в `main`. Workflow `build.yml` проверит справочные данные,
   Python-тесты, формат версии, версию внутри `IBStart.exe`, CTest и предел размера
   8 МиБ. Для PR с изменениями, запускающими релиз, он также проверит отсутствие
   соответствующего тега `v<версия>`. Отдельный `codeql.yml` выполнит статический
   анализ C++ на фактической MSVC/CMake-сборке; его результаты доступны в GitHub
   Code Scanning. Локальные проверки не заменяют результаты этих workflow.

Для 0.8.0 подготовлен [протокол проверки релизной ветки](verification-release-0.8.0.md).
Он фиксирует состав объединения, исправления и границы локальной проверки.

## Обновление сайта и документации

Workflow `pages.yml` проверяет сборку сайта в PR и публикует его после merge в `main`, если изменились `docs/**`, `CHANGELOG.md`, `mkdocs.yml`, `requirements-docs.txt` или сам `pages.yml`. Для публикации в настройках репозитория источником GitHub Pages должен быть выбран **GitHub Actions**.

Для такого PR не требуется увеличивать версию приложения: `build.yml` пропускает проверку свободного тега, если все изменённые файлы входят в список исключений релиза. Его сборка и тесты при этом выполняются. Изменение только `README.md` не перестраивает сайт, так как README не входит в его исходные файлы.

Изменения `tools/**` и `src/core/launcher/**` также запускают сборку Pages.
Актуальность текстов,
ссылок и снимков проверяйте до публикации; номер в исходниках не означает, что
соответствующая версия уже доступна в последнем GitHub Release.

### Обновление снимков окон

Снимки на страницах соответствуют **IBStart 0.8.0**. Основной набор подготовлен
20 октября 2026 года; вкладка «Запуск» обновлена 21 октября при проверке релиза.
Они используют демонстрационные названия, адреса и учётную запись с пустым паролем.
Файловые базы на снимках не существуют: программа показывает их состояние как недоступное.
Число найденных платформ и их полные версии зависят от компьютера, на котором сделан снимок.

1. Соберите текущую Release-версию.
2. Подготовьте отдельную portable-копию с вымышленным каталогом; папка назначения должна быть новой:

   ```powershell
   python docs/scripts/prepare-screenshots.py --exe out/build/msvc-x64-release/IBStart.exe --output out/docs-demo
   ```

3. Откройте созданный `out/docs-demo/IBStart.exe`. Снимайте главное окно, редактор базы,
   дополнительные настройки, разовый запуск, конструктор, настройки приложения и формы учётных записей.
   Для снимка конструктора из меню выберите показательный пример с аргументами и опциями;
   при вызове из поля проверьте кнопку возврата **Применить**.
4. Сохраните снимки в `docs/images/` в формате PNG без изменения содержимого элементов интерфейса.
   Включите каждый используемый снимок в соответствующую страницу и обновите дату и версию в этом разделе.
5. Выполните строгую сборку сайта с временной копией `CHANGELOG.md` в `docs/changelog.md`;
   удалите временную копию после проверки. Проверьте изображения и переходы в собранных страницах,
   включая ссылки **Изменить** и **Просмотреть исходник** страницы «Что нового».

Сценарий подготовки демонстрационного профиля находится в
[исходниках проекта](https://github.com/ant-m13/ibstart/blob/main/docs/scripts/prepare-screenshots.py)
и не входит в опубликованный сайт или поставку приложения. Он отказывается перезаписывать
существующую папку. Во время съёмки не требуется запускать 1С, очищать кэш или сохранять изменения баз.

## Автоматический выпуск после merge

После принятия PR workflow `release.yml` работает с точным коммитом, появившимся в `main`, и последовательно:

1. через GitHub API подтверждает, что коммит появился в `main` после принятия PR (прямой push не выпускается);
2. проверяет воспроизводимость справочных данных, запускает Python-тесты,
   повторно собирает Release и запускает CTest;
3. проверяет `ProductVersion` готового `IBStart.exe`;
4. создаёт portable ZIP с пустым маркером `IBStart.portable`, SHA-256 `checksums.txt` и release asset `IBStart.version` с SemVer-версией;
5. создаёт аннотированный тег `v<версия>` на этом коммите;
6. публикует стабильный GitHub Release `IBStart <версия>` с заметками текущей версии, EXE, portable ZIP, `checksums.txt` и `IBStart.version`.

Повторный запуск workflow безопасен: существующий тег принимается только тогда, когда он указывает на тот же коммит, а assets релиза обновляются через `--clobber`. Если версия уже относится к другому коммиту, выпуск останавливается — необходимо создать новый PR с увеличенным номером.

Нельзя добавлять упаковщики EXE, автоматическую установку обновлений, телеметрию
или секреты в артефакты. Проверка версии выполняется по ручной команде либо при
запуске, если включена настройка; она открывает страницу GitHub Release по действию
пользователя и не скачивает или заменяет EXE. Перед merge вручную проверьте приложение
на поддерживаемой Windows и убедитесь, что в логах нет пароля, токена либо строк
`/P` с исходным значением.

Изменение только `.github/workflows/release.yml` не запускает выпуск. Если вместе с workflow меняется приложение, после merge проконтролируйте результат релиза. Для публикации у workflow задано разрешение `contents: write`.
